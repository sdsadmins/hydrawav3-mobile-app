## 2026-08-01

| ID | Title | What changed | File(s) |
|----|-------|--------------|---------|
| B-40 | **Session history only saved if the user tapped "Save & done"** | The `/intake` POST was deferred to the after-screen's button, so a run the user walked away from (or whose after-screen never opened) was **never written to history** — it only lingered as a "Needs review" card. History now saves on its own: `PendingOutcomesNotifier.autoLog` finalizes the record when the after-screen is left by **any** route (back gesture, nav tab, system back), carrying whatever the pulse check answered; `autoLogUnreviewed` sweeps anything still queued on app start (app killed mid-review, run ended before this build). The button is now a shortcut, never a requirement. An `_underReview` set holds the auto-save back only while the after-screen is actually on screen, so the answer still rides along on the single POST (the backend inserts a new intake per POST — there is no upsert, so it must fire exactly once). | `session/presentation/providers/pending_outcomes_provider.dart`, `session/presentation/screens/session_after_screen.dart` |
| B-42 | **Ring turned break-coloured after the first break** | The live ring's `--gc` accent is re-resolved **per sub-protocol** from the protocol name, and `GoalColor.of` returns `#4E7A8A` for **Calm** — byte-for-byte the same value as `_kBreakColor` / the handoff's `BREAK_COL` (`hw_tokens.dart:301` vs `app.js:1274`); **Recovery**'s `#2F4A5A` is the same blue a shade darker. So a stack starting on a copper (Performance) protocol looked right, then the moment it switched to a Calm/Recovery stage the ring arcs, progress bar, stage chips, active-stage name and legend **all** repainted in the break colour and the whole ring read as one long break. New `_protocolAccentColor` keeps the protocol accent out of the break's hue window (±25°, measured on `HSLColor.hue`): Calm (Δ0.0°) and Recovery (Δ6.3°) fall back to the default Performance copper; Comfort (Δ171.8°) and Vitality (Δ43.0°) are nowhere near it and keep their own colour. Blue now belongs to the break alone. **Ring geometry/design untouched** — colour resolution only. | `session/presentation/screens/session_screen.dart` |
| B-45 | **Post-session screen asked only the first question, as a guessed YES / NO** | The screen rendered an "outcome pulse": `_pulseTarget` returned the **first question of the first protocol** that had any and stopped, and `_matchPreset` then built two buttons by scanning that question's answers for one containing `yes/better/good` and one containing `no/same/worse`. So on the real record for **PNF Active Training 3** (`69870a44b817549cad1e1968`) — 2 questions, the first with 3 options — question 2 was never asked and the third option (`fd`, rank 3) had no button that could select it: 2 of 5 configured answers were reachable. Rebuilt to render every protocol section, every question numbered, and **every configured answer as its own chip** in the admin's order (free-text field where a question has no presets), plus a **Remarks** field — the same content `showPostSessionOutcomesSheet` already had, which was the only place they'd ever appeared. Answers are collected per question with the preset's own rank (`rankForAnswer`, 0 for free text), so a partly-filled form still records what was answered; the button reads "Save & done (N left)" rather than silently discarding it. Stopped-early runs still record no outcome (existing rule) but now keep remarks. Covered by `test/session/session_after_screen_test.dart`, shaped on the real backend record. | `session/presentation/screens/session_after_screen.dart`, `test/session/session_after_screen_test.dart` |
| B-44 | **Finished session stayed "1 session running" and kept its devices locked "In use"** | Ending the backend session lived on `SessionScreen._handleTerminalSessionState`, which only runs **while that screen is mounted**. A run that finished while the user was on the devices list — or was watching it in remote view — therefore never POSTed its stop: `GET /sessions/active` went on returning it, so the live banner kept announcing "1 session running" and [busyDevicesProvider] kept its devices greyed out as "In use" **permanently**, until someone re-opened the run and hit Stop All. (Protocol Plus runs were already safe — `ProtocolPlusController` has its own app-scoped engine listener; only normal runs were orphaned.) The stop moved into `SessionEngine` itself, on a `addListener` hook that catches **every** terminal transition — timer completion, Stop All, a firmware `rs:stop`, a device dropping off — with no screen involved. Added `markBackendSessionEnded()` for the case where the server side is already gone (stopped from the web / another phone) so the engine doesn't POST a redundant stop. New `finishedOwnSessionIdsProvider` (backend id ↔ local engine status) additionally drops finished runs from the banner and the busy/plan-limit sets so the device frees instantly instead of on the next 1s feed poll. | `session/services/session_engine.dart`, `session/presentation/providers/live_sessions_provider.dart`, `session/presentation/providers/busy_devices_provider.dart`, `session/presentation/widgets/live_sessions_banner.dart`, `session/presentation/screens/session_screen.dart` |
| B-43 | **Ring segment boundaries were rounded, with a gap** | Each protocol / break arc was drawn with `StrokeCap.round`, so every segment bulged half the stroke (≈0.012 of a turn at 13px on this radius) past its own sweep at both ends — which is exactly what the `gapFraction = 0.012` spacer was cancelling out. Segments now use `StrokeCap.butt` and no gap at all, so the ring is a **solid unbroken circle cut by straight edges**: the colour change at each boundary is the divider. The plain single-protocol arc keeps its round cap (it has no boundaries to draw). | `session/presentation/screens/session_screen.dart` (`_TimerRing.paint`) |
| B-41 | **Post-session screen only appeared when the run ended on the live card** | `SessionScreen` owned the navigation to `#scr-ready-after` and bailed out for `remoteView`, so ending a run from the **devices list** (live banner → remote view) or simply while the user was on another screen showed nothing. Navigation moved out of the screen into a new app-wide **`SessionOutcomeGate`**, mounted above the router in `HydrawavApp`: it watches the pending-outcomes queue (which `SessionEngine` fills on every terminal transition, screen or no screen) and opens the after-screen from wherever the user is — replacing the live card when it's open, pushing on top otherwise. Same ending everywhere. `stoppedEarly` is now stamped onto the queued snapshot by the engine, so the screen renders the same copy with no live engine to read from; the screen's `stoppedEarly` / `remainingSeconds` args became optional overrides. | `session/presentation/widgets/session_outcome_gate.dart` (new), `app.dart`, `session/presentation/screens/session_screen.dart`, `session/presentation/screens/session_after_screen.dart`, `session/domain/pending_session_outcome_model.dart`, `session/services/session_engine.dart`, `core/router/app_router.dart` |

## 2026-06-17

| ID | Title | What changed | File(s) |
|----|-------|--------------|---------|
| B-24 / F-11 | **90-second break between stacked protocols + highlight next** | Completed the partial B-32 work with a **live break countdown / idle UI**. The engine predicts each protocol's runtime locally (mirroring the server's `getProtocolDurationSeconds + delay` switch schedule) and, once a Plus protocol's time elapses but the next `START_PROTOCOL` switch hasn't landed, flags the device **on break** with a counting-down `breakRemaining`. The switch landing (`applyProtocolPlusSwitch`) authoritatively ends the break and re-bases the next segment. UI: the session tracker shows a **"BREAK · Next: \<protocol>"** banner with a live `M:SS` countdown, the finished stop collapses to ✓ (past), the next stop pulses as **"UP NEXT"** (hourglass), and the connector between them shows the live remaining seconds (falls back to **"SWITCHING…"** if the server switch runs late). | `session/services/session_engine.dart` (segment-end tracking + `_computeBreakState`), `session/presentation/screens/session_screen.dart` (break banner, `isNext` route stop, active route track) |
| B-24 (follow-up) | **Stop button unusable during the stack break** | The firmware physically stops and **drops the BLE link during the break gap**, which tripped the existing "disconnected → disable controls" guard and greyed out Stop. Now the Plus Stop button stays enabled during a break (`blockStop = disconnected && !plusOnBreak`), and `stopDevice` for a Plus device skips the unreachable BLE STOP write but **still ends the run locally** — the controller then cancels the remaining server-scheduled `START_PROTOCOL` switches via `stopServerSession()`. Normal (non-Plus) runs keep the old guard. | `session/presentation/screens/session_screen.dart`, `session/services/session_engine.dart` |

| B-33 | **Device Fleet / WiFi list spins forever for some accounts** (e.g. admin `596`; practitioner `525` was fine) | Root cause: an **infinite token-refresh loop** in the auth interceptor — a 401 (role with no access to `/admin/sensors/organisation/{id}`) triggered a refresh, then retried via `djangoDio.fetch()` which **re-runs the whole interceptor chain** → 401 → refresh → retry → … forever, so the caller's `Future` never completed. Added a **one-retry guard** (`requestOptions.extra['__authRetried__']`) so a second 401 propagates instead of looping. | `core/network/auth_interceptor.dart` |

Removed the invalidate — the provider already re-runs (and returns `[]`) when auth state resets. | `auth/.../auth_provider.dart` |
| B-35 | **Devices page showed the previous logged-in user's devices** | Provider fell back to "**first org** in `/admin/organizations`" whenever the profile lacked an org id, and the org id wasn't being parsed from the login/profile JSON. | B-36 | **Device fetch threw a red error on 401/403/404/204** instead of showing empty | `getDevicesByOrg`/`getDevices` now return `[]` for 401/403/404/204 (no access / no devices), matching the web's `getSensorsByorgId`. Fleet page also renders empty/last-known value instead of an infinite spinner (extends B-20 to the registration screen). | `devices/data/device_remote_source.dart`, `devices/.../device_register_screen.dart` |
| B-37 | **No pull-to-refresh** on Device Registration & Protocol List (Home) pages | Added `RefreshIndicator` to both — fleet re-fetches `wifiDevicesByOrgProvider` (pull works even on empty/error states); Home re-fetches `protocolListProvider` + `goalTagListProvider`. | `devices/.../device_register_screen.dart`, `protocols/.../protocol_list_screen.dart` |
